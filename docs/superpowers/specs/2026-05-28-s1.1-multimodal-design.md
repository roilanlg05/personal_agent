# S1.1 — Re-habilitar multimodal (imagen + audio) en LiteRT-LM — Diseño

> **Padre:** roadmap `00-roadmap.md` §3.1, pendiente S1.1 #5 ("modalidad imagen"). Amplía el alcance a **imagen + audio** (E4B oficial soporta ambos). Se solapa con S9 (visión) y adelanta parte de S10 (audio ≤30s).
> **Fecha:** 2026-05-28. **Dispositivo de verificación:** iPhone 16 físico (`00008140-000A6216110A801C`), GPU/Metal.

---

## 1. Problema

El runtime LiteRT-LM cargó solo texto: en `LiteRTLMRuntime.load` el `EngineConfig` deja `visionBackend`/`audioBackend` en `nil`, así que los executors multimodales nunca se inicializan. `generate()` ya arma el `Message` multimodal con `.imageFile`, pero sin vision executor la imagen se ignora o falla. La causa de haberlo deshabilitado fue el error histórico `NOT_FOUND: TF_LITE_VISION_ENCODER` al pedir un vision backend (presuntamente sobre un archivo sin encoder); se quitó para arreglar el load text-only.

El `ModelDescriptor` ya declara `supportsImage`/`supportsAudio` (true para E4B y E2B oficiales, que sí son multimodales), pero esos flags **no llegan** al runtime: `ModelLoadOptions` solo transporta `modelPath` y parámetros de generación.

## 2. Objetivo

Cargar los executors de visión y audio cuando el modelo los soporta, de forma robusta (sin romper el load si un archivo carece del encoder), y verificar en device que una foto y un clip de audio corto producen respuesta. Backend de vis/audio: **GPU con fallback a CPU** (decisión del brainstorming).

No-objetivos: cambiar la UI de chat más allá de reflejar el estado multimodal; pipeline de audio en vivo / grabación (eso es S10/S2); cualquier cosa de llama.cpp (S1.1 #1).

## 3. Diseño (Enfoque A — capability-gated + fallback en cascada)

### 3.1 Flujo de capacidad (descriptor → runtime)

`ModelLoadOptions` gana dos campos:

```swift
public var supportsImage: Bool   // default false
public var supportsAudio: Bool   // default false
```

Default `false` preserva compatibilidad (DummyRuntime, tests text-only, llamadas existentes). En `HarnessModel.toggleLoad`, donde ya se resuelve el `descriptor` (HarnessModel.swift ~L94-108), se capturan `descriptor.supportsImage`/`supportsAudio` en variables visibles fuera del `if let` y se pasan al `ModelLoadOptions` (~L113-119). El runtime decide **declarativamente** si pedir cada executor.

### 3.2 Cascada de fallback en `LiteRTLMRuntime.load`

Se refactoriza el bloque de `EngineConfig` (LiteRTLMRuntime.swift L33-45) a un helper que intenta crear + inicializar un `Engine` con backends de vis/audio dados, y una cascada que solo desciende cuando una modalidad declarada como soportada no arranca:

```
solicitadas = (img: supportsImage, audio: supportsAudio)

intento 1: vis/audio = backend principal (GPU)         → si OK, listo
intento 2: vis/audio = .cpu()  (solo las solicitadas)  → si OK, listo (degradado a CPU)
intento 3: vis/audio = nil     (text-only)             → si OK, listo (multimodal off)
intento 4: (mismo text-only ya falló) → propagar error  (modelo realmente inválido)
```

Reglas:
- Si una modalidad **no** estaba solicitada, su backend es `nil` en todos los intentos (no se degrada algo que no se pidió).
- Cada intento construye un `EngineConfig` nuevo (struct inmutable) y un `Engine` nuevo; el LLM mantiene siempre el `backend` configurado por el usuario (GPU por defecto). Solo el backend de vis/audio degrada.
- Si las modalidades solicitadas eran `(false,false)`, la cascada arranca directo en text-only (un solo intento) — equivale al comportamiento actual.

### 3.3 Estado observable de multimodal

`load` registra qué modalidades quedaron activas:

```swift
private var visionEnabled = false
private var audioEnabled = false
public var multimodal: (image: Bool, audio: Bool) { (visionEnabled, audioEnabled) }
```

Uso:
- `streamGeneration` solo construye el `Message` con `.imageFile` si `visionEnabled`; si llega una imagen y la visión no cargó, degrada a prompt de solo texto (no manda una imagen que el engine ignoraría/rechazaría). Análogo para audio cuando se agregue el contenido de audio al `Message`.
- `HarnessModel` lee `multimodal` tras cargar para que `statusMessage` indique degradaciones (p. ej. "cargado · imagen: GPU, audio: CPU" o "imagen no disponible").

> Nota: la API actual `generate(prompt:image:options:)` solo recibe imagen. Se extiende la firma del protocolo `ModelRuntime.generate` con un parámetro opcional `audioURL: URL? = nil`, fluido igual que la imagen (escritura a temp file → `.audioFile(path)` en el `Message`). `DummyRuntime` lo ignora; las llamadas existentes no cambian (default `nil`). La **integración de audio en la UI de chat** (grabar/elegir clip) es de S10 y queda fuera — aquí el parámetro existe para que el test lo ejercite y para dejar el runtime listo.

## 5. Riesgos

- **El archivo E4B instalado podría carecer del vision encoder** pese a `supportsImage:true`. La cascada lo absorbe (cae a text-only), pero entonces la imagen no funcionará y habrá que re-descargar la variante multimodal correcta. La verificación en device es la que confirma cuál es el caso real.
- **Costo de RAM del vision/audio executor** sumado al E4B en GPU: ya usamos la entitlement `increased-memory-limit`; vigilar RSS en device, podría forzar vis/audio a CPU de forma permanente.
- **Conmutar backend de vis/audio recompila shaders** en frío (igual que el LLM); el primer load multimodal será más lento.

## 6. Entregables

1. `ModelLoadOptions` + `supportsImage`/`supportsAudio`.
2. `HarnessModel.toggleLoad` propaga los flags del descriptor.
3. `LiteRTLMRuntime.load` con cascada GPU→CPU→text-only + estado `multimodal`.
4. `streamGeneration` respeta `visionEnabled`/`audioEnabled` (degradación segura).
5. Tests: text-only no rompe, audio (con asset + skip), imagen verde en device.
6. `statusMessage` refleja el estado multimodal; `graphify update .`.
